The build

Server-rendered, no framework, no build step

Flask with thirteen blueprints, Jinja2 templates, vanilla JavaScript that initialises from data attributes, and raw psycopg2 against PostgreSQL with no ORM and no migration tool.

Administration is the gate

Nothing else in the system proceeds until the registration queue is worked. Staff open each applicant's uploaded documents, compare them against the stated details, and approve or reject.

Approving is what mints the invitation token. There is no other route to an account. Once a decision is recorded, the document images are deleted and only a SHA-256 digest, the byte size, the extension and the outcome remain, which is enough to prove what was reviewed without holding copies of government IDs indefinitely.

Three staff tiers share this console. Super User is an Admin minus user management; Secretary is a Super User minus PV consultations.

Solara answers from documents, not memory

Chat replies are built from a curated knowledge base of ten source documents, chunked and embedded, retrieved by brute-force cosine similarity over PostgreSQL REAL arrays. A tuned similarity floor discards weak matches rather than answering from a bad one.

Off-topic questions are refused deterministically before any chat call: a keyword allowlist first, then a cheap yes-or-no gate only if that misses. This exists because relying on the chat model itself to decline was unreliable on Taglish input.

Re-indexing after editing the knowledge base is a manual terminal command, never an action the running app can take.

Instruction

  • Grading queue flagging what auto-grading could not settle

Learning

  • Syllabus resolved from the approved programme, not identity
  • Timed quizzes, automatic grading for three of four types
  • In-module AI assistant answering questions on the material
  • Progress computed identically for trainee and trainer views

Consultation

  • Structured site survey with electricity-bill OCR
  • Deterministic engine: sizing, cost, savings, payback, yield
  • English and Taglish, with source citations
  • Engineer review stored alongside computed figures, never over them

Payments

  • Card and QRPH checkout for individual enrolment
  • Corporate invoicing from an approved roster, audited overrides
  • Database-level idempotency keys prevent double-charging
  • Unmatched webhooks quarantined raw, never dropped

Certification

  • Issuance gated on completing every module in the programme
  • Certificate hash anchored to Polygon at issue
  • Public QR verification with transaction, block and confirmations
  • Re-anchor action for certificates issued while offline

Decisions worth defending

Four choices that explain most of the otherwise-odd code.

A

The schema lives in code

One function is the entire schema: CREATE TABLE IF NOT EXISTS, plus idempotent ALTER TABLE ADD COLUMN IF NOT EXISTS, plus inline backfills. It re-runs on every boot, so a fresh clone and a long-lived database converge on the same 36-table shape without a migration tool. To add a column you append an idempotent ALTER, because nothing reads migration files.

B

One capability map, consulted twice

No route compares a role string inline. A single map takes capability to roles, and it is exposed as a template global, so a hidden button and the route behind it read the same table and cannot disagree. Per-account overrides let one trainer run training modules and another PV consultations without inventing a new role.

C

Blockchain writes are best-effort

Payments and certificates are valid whether or not the Polygon write lands. Failures are logged and surfaced in the interface as "Off-chain" with a re-anchor action. They are never swallowed silently, and they never abort the transaction that triggered them.

D

A join code names a class, it never authorises

Entitlement is re-derived on every access, so a membership row is not standing authority. A later rejection, roster revocation or cancelled invoice closes access without anyone deleting the row. Two exceptions are documented and accepted knowingly: individual enrolment is never gated, and access stays open until a class actually exists.

Three independent provider settings govern AI use: one for text generation, one for vision, one for embeddings. The split is deliberate. A model good at reading a government ID is not the one you want writing quiz questions, and changing the chat model must never force a re-index of the retrieval corpus.

How it is checked

There is no automated test suite. The standing check is a compile pass and an import pass, then exercising the route in a browser. Beyond that, a handful of purpose-built scripts guard the specific regressions a compile pass cannot catch.

A separate development harness serves the real application on a second port with a live trace of each consultation turn: the gate decision, every retrieved chunk with its score, what the extractor banked, the preview calculation, per-stage timings, and the exact prompt sent. It instruments the blueprint by monkeypatch from that process alone, so no development-only branch exists in a shipped route.
